# ChatGPT plugin

The distributable package is built from [`plugin/`](../plugin). Run `npm run plugin:package` to create `dist/vitalog-plugin.zip`. The script validates both manifests against the pinned Agent Plugins 1.0.0 schemas, verifies the transparent brand assets and every archive entry, and packages only six allowlisted files. CI uploads the zip alongside verification reports.

The archive uses root `plugin.json` and `mcp.json`, OpenAI presentation metadata, the Vitalog red heart mark, and one skill for using the ledger. It declares the Streamable HTTP endpoint `https://vitalog-api.praveent.com/mcp`. Authentication is implemented by the server; the archive contains no API keys, root credentials, OAuth codes or tokens.

## Connect after deployment

When you connect the plugin, Vitalog opens its **Connect ChatGPT** page. Sign in with your configured root email and password and approve the requested access. Vitalog returns a short-lived authorization code to ChatGPT's callback. ChatGPT exchanges it for a 30-day MCP access token automatically. You do not need to generate, paste or copy an API key, and your password stays with Vitalog.

This follows [ChatGPT's authorization-code OAuth flow with PKCE](https://developers.openai.com/plugins/build/auth). The token is delivered in the private token-exchange response; the browser callback contains only the code, state and issuer.

1. Merge and deploy the follow-up changes. Startup applies the Drizzle migrations, including `0005_oauth_root_sign_in`, before serving requests. Configure `ROOT_EMAIL` and `ROOT_PASSWORD` for sign-in.
2. Upload `vitalog-plugin.zip` in ChatGPT's **New Plugin** dialog. Connect the declared MCP server with OAuth when prompted.
3. On Vitalog's **Connect ChatGPT** page, enter your root email and password, review the requested access and select **Connect ChatGPT**. Credentials are sent only in the private JSON request body to Vitalog. The page clears the password after submission and when leaving the page.
4. Use the plugin to query or log the observations you supply. Reconnect by signing in again after 30 days. The primary `AUTH_KEY` can list and revoke the connection through the existing API-key management endpoints; revoking its record blocks access on the next MCP request. Revoke-all also cancels pending authorization codes.

This is a package for personal upload. Public-directory submission has separate publisher, domain-verification and review requirements. No public publication or ChatGPT account installation is performed by packaging the archive.

## Issuer and authentication

Production uses API issuer `https://vitalog-api.praveent.com` and MCP resource `https://vitalog-api.praveent.com/mcp`. Set API `PUBLIC_BASE_URL` explicitly and include its host in `ALLOWED_HOSTS`. Set `UI_BASE_URL=https://vitalog.praveent.com` on both services and `API_BASE_URL=https://vitalog-api.praveent.com` on the UI. Public values are provided at runtime; the UI has no root/API/database secrets.

The API authorization endpoint validates ChatGPT's request and sets a signed, host-only API cookie before redirecting to `https://vitalog.praveent.com/oauth/authorize`. The separate Next.js screen fetches consent state and submits approval directly to the API with credentials included. Exact-origin CORS permits only the configured UI on `/oauth/request` and `/oauth/approve`. The two HTTPS subdomains share a browser site, so SameSite=Lax works while the HttpOnly cookie remains scoped to the API host. Deploy them on sibling subdomains under the same registrable domain and scheme. API-key creation permits the UI origin without cookies; CORS does not expose ledger, administration or token-exchange routes.

The issuer must be a canonical HTTPS origin without a trailing slash, in the API host allowlist; loopback HTTP is permitted for development. When omitted, a single public host can infer the issuer. Multiple public hosts require an explicit issuer. OAuth routes are disabled without an issuer. Moving from the original host changes the OAuth audience: existing tokens and pending flows for `vitalog.praveent.com/mcp` cannot authenticate the new resource. Re-upload the updated plugin and reconnect. Manual API keys and ledger data remain valid; update REST clients to the new API hostname.

Vitalog serves protected resource metadata at `/.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp`, and authorization server metadata at `/.well-known/oauth-authorization-server`. An unauthenticated `/mcp` response advertises the resource metadata in `WWW-Authenticate`.

The authorization server accepts ChatGPT's stable Client ID Metadata Document at `https://chatgpt.com/oauth/client.json`. It fetches only that exact HTTPS URL, rejects redirects, limits the response to 8 KiB with a five-second timeout, verifies the advertised public-client method and exact callback, and caches successful validation for ten minutes. Other client URLs, DCR and non-ChatGPT callbacks are not supported. The callback is `https://chatgpt.com/connector_platform_oauth_redirect`. Successful and denied consent responses include the exact issuer in `iss` and preserve `state`. Authorization errors for that exact client and callback also return there with `error`, `iss` and the original valid `state`; unknown or ambiguous client/callback values stay local. An error clears the pending flow cookie and never issues a code.

Authorization requires S256 PKCE, an exact `resource=<issuer>/mcp`, root email/password sign-in and explicit consent to the requested scopes. API keys and `AUTH_KEY` do not replace this sign-in. A signed HttpOnly SameSite=Lax flow cookie expires after five minutes; HTTPS cookies use the Secure flag and `__Secure-` prefix. Approval requires the exact configured UI Origin and matching CSRF token. It accepts JSON only and shares the API-key page's root-authentication limits: five attempts per address and thirty per process per minute, at most two concurrent scrypt verifications, and `Retry-After: 60` when limited. Authentication bodies are bounded to 4 KiB.

Codes expire after five minutes and are stored only as hashes. Sign-in and consent issue only the code; no key or access token exists yet. Exchange uses form-encoded `authorization_code`, with exact client, callback, resource and PKCE binding. A PostgreSQL transaction locks the code, creates the token and its management record, and consumes the code once. Concurrent exchanges cannot issue two tokens, and an insertion failure rolls back both key creation and consumption so the exchange can be retried. There is no implicit, password, client-secret or refresh grant. Issuance, exchange and OAuth authentication trigger cleanup at most once per process per minute, sharing concurrent cleanup work. Each batch deletes up to 1,000 codes and 1,000 tokens whose own lifetime or management record has expired or whose record was revoked, skipping locked grants. Additional batches run on subsequent OAuth traffic; cleanup leaves API-key metadata, active grants and health records intact.

OAuth access tokens use a separate `vlo_` prefix and 32 random bytes and are stored only as SHA-256 hashes. Exchange creates a record in `api_keys` for the same token digest with a `vlo_…` hint and a 30-day lifetime from issuance; the OAuth table adds audience and scopes. The existing primary-key management APIs list and revoke this record without returning the token or hash. The MCP resource checks token audience, token and management-record expiry, revocation and scopes on every request. OAuth tokens grant MCP access only; they cannot access REST or key administration. Manually generated `vlk_` API keys retain their REST/MCP behavior and the primary environment key retains exclusive key administration. Existing grants linked to previously generated keys remain usable at their original resource until their original expiry or revocation; the forward migration preserves those rows and code exchange supports their bindings.

`health:read` permits read tools and `health:write` permits mutation tools. Each tool advertises its required OAuth scope. Missing permissions return an MCP OAuth challenge without executing the operation. Tokens and authorizations survive server restarts; expiry and revocation have no application cache. Primary-key rotation preserves issued access tokens but invalidates pending signed browser consent cookies. Restoring an older backup can also restore a previously revoked connection; revoke restored keys before exposing a restored database.

## Verification

Run `npm run verify`, `npm run test:auth` and `npm run test:oauth`. The OAuth command creates and removes a disposable PostgreSQL 17 database and tests both the actual Hono routes and the official MCP client. It covers direct root sign-in, issuance only at exchange, shared authentication limits, atomic rollback, PKCE and audience binding, one-time/concurrent code exchange, cookie/CSRF/origin protection, hash-only storage, permission enforcement, expiry, restart, primary-key revocation/revoke-all including pending codes, legacy key-bound grants, bounded attempts/bodies, untrusted client metadata and log privacy. Client metadata uses a deterministic fixture matching the published ChatGPT CIMD document; this is not proof of a live ChatGPT account link. The ignored report is `.test-artifacts/oauth.json`.

The package format follows [OpenAI's plugin packaging documentation](https://developers.openai.com/plugins/build/plugins). The flow follows its [MCP authentication documentation](https://developers.openai.com/plugins/build/auth). Packaging and local protocol checks do not verify a production deployment or a successful ChatGPT upload; those must be checked after merge and deployment.
