The Next.js app uses the Apache-2.0 `@avgeek-oss/design-system` package on HeroUI, with Vitalog's red theme and heart mark. Its page layouts, authentication forms, sidebar, navbar, buttons, widgets, code blocks, tables, and dialogs use the package's public exports. The unmodified 1.2.6 release archive is pinned in `vendor/` for builds without registry credentials. Stats contains Daily View and Weight Management; Settings contains one Account settings entry. Secondary navigation groups Profile and Preferences under Account, and API Keys, MCP Connections and MCP Guide under API & MCP, without a duplicate sidebar title. The primary sidebar footer shows the saved name and Gravatar. Team and Security settings are omitted. The desktop sidebar can be collapsed and remembers its state. On smaller screens, the header toggle opens an accessible navigation drawer with the settings sub-navigation. The shared theme switcher remembers light, dark, or system preference. `/login` signs in with the configured root email and password. `/daily` shows the server's current local day; `?date=YYYY-MM-DD` selects a past date through the shared date-picker input. Wide screens place the summary on the left and Logs on the right; smaller screens stack Logs below the summary. Nutrition fills the summary width, with protein/carbs and fat/fiber in two rows. Mood/water and active calories/exercise minutes form two more pairs of cards. Logs include all active record types for the selected day, with an event time when one was supplied and minimal expandable details. A date-only observation does not acquire an invented event time.

`/weight` shows the latest usable scalar weight on or before today, in kilograms, plus a 30-day chart and weigh-in history. A weight goal supplies the explicit start `baseline` and target. The UI reads the API's observed goal progress. Changing the target preserves the baseline unless a client explicitly replaces it through REST or MCP. It does not infer a baseline from the earliest observation. Qualified or excluded readings cannot become the current weight. The viewing UI has no health-record or goal creation, editing or deletion controls.

Unknown values display a dash. Explicitly supplied zero values display zero. Nutrition follows the API's daily-total precedence and compatible-definition rules. Water is logged water rather than all fluids. Exercise cards use active energy and explicitly supplied exercise duration, with reported daily totals taking precedence over workouts and unresolved overlaps left unknown. Goals appear only when they were configured for that day. Nutrition values are upper limits; water and exercise are minimum targets. Nutrition progress fills are grey below 90% of the limit, green from 90% through 100%, and red when the limit is exceeded. Minimum and weight targets remain grey while in progress and green when met. The data reads are bounded: at most 1,000 daily records and 10,000 weight records can be displayed; exceeding a bound produces an error instead of a partial total. Chart points are observed readings; connecting lines do not create new observations.

## Browser sessions

`API_BASE_URL` remains the browser-accessible API origin for API-key generation and OAuth. Server reads use the optional `API_INTERNAL_BASE_URL`, falling back to that public origin. Compose sets the internal origin to `http://api:3000` and allows that Host on the API. The private origin is never passed to client components or added to browser CSP. Towbar can continue using the existing public HTTPS origin; a private override requires its hostname to be included in the API's `ALLOWED_HOSTS`.

The UI server forwards root credentials once to `POST /auth/session`. The API issues a random, opaque `vls_` token with a 30-day expiry. It uses the existing hashed-token and revocation tables, with a distinct browser resource and read-only scope. No extra UI secret is needed. Migration `0012_root_account_settings` stores the account display name and presentation preferences independently of the environment-managed email and password. Root sign-in shares the API-key/OAuth scrypt and rate protections. All health data is fetched by the Next.js server; it does not provide a general-purpose browser API proxy.

On HTTPS the token lives in `__Host-vitalog-session`, a Secure, HttpOnly, host-only cookie with SameSite=Lax and path `/`. Loopback HTTP uses `vitalog-session` without Secure. The token is never returned in browser JSON, server-rendered page content, localStorage or sessionStorage. Protected pages are dynamic and use uncached API reads. `GET /auth/session` validates the token and returns its expiry, server timezone, today's date and the account name, email and date/time preferences. `DELETE /auth/session` revokes only the authenticated session. The UI's `/auth/login` and `/auth/logout` routes require the exact configured UI Origin, preventing cross-site login and logout requests.

Browser sessions can read domain REST routes. They can list external API-key metadata and update their account name and preferences. They cannot mutate records or goals, create/revoke API keys, read operator readiness/OpenAPI, or access MCP. Generated API keys and MCP OAuth retain their existing privileges. The environment `AUTH_KEY` can list browser sessions alongside API keys and MCP connections; their hints begin with `vls_`. Individual or revoke-all administration affects subsequent reads. Logout clears the cookie and attempts server revocation; if the API is unavailable, it clears the browser cookie and reports that remote revocation did not complete. A request that was already authenticated may finish.

`/api-keys` and `/oauth/authorize` continue to serve API-key generation and MCP consent independently of the dashboard session. The production hostnames remain `vitalog.praveent.com` for UI and `vitalog-api.praveent.com` for API/MCP. Use the existing Towbar services; building this UI does not deploy it.

## Profile and preferences

`/settings/profile` uses the shared profile form to update a display name (1–120 characters) and links the Gravatar image to its avatar editor. Email and password stay in `ROOT_EMAIL` and `ROOT_PASSWORD`; the app does not edit them. A failed or expired-session save keeps the entered name for retry. Responses arriving after navigation do not show stale success or error notifications. Gravatar receives only the normalized email SHA-256 hash, with no referrer, and falls back to initials when no image exists.

`/settings/preferences` uses the shared date/time preferences form, including searchable IANA time zones and a live preview. Date/time options come from the published React-free `utilities/date-time-preferences` catalog; contract tests keep the API constants aligned without adding UI dependencies to the API image. `PATCH /auth/profile` and `PUT /auth/preferences` require a valid browser session and strict JSON. The UI proxy additionally enforces the exact UI Origin, caps request bodies at 4 KiB, and never exposes session tokens. New display preferences default to day–short month–year, 24-hour time and UTC, matching Towbar. Migration `0013_account_preference_defaults` changes column defaults without rewriting saved preferences; all five date IDs and four time IDs remain valid. Values persist in PostgreSQL across sign-out and restarts and remain unchanged if environment credentials rotate. Preferences format log times, weight history, chart tooltips, and API-key metadata. Calendar-only dates are preserved. Daily totals, goal effective dates and today's selected ledger date continue to use their existing recorded/server-date semantics; changing the display time zone does not move records between days.

## API Keys, MCP Connections and MCP Guide

`/settings/api-keys` provides the same create-and-reveal dialog and key-table composition as the other OSS apps. Keys have no name and expire after 30 days. The complete secret appears only in the creation dialog; the table contains hints and expiry metadata. Revoked keys are filtered on the server before pagination. `/settings/mcp-connections` lists OAuth clients, their approved permissions and expiry. Revoke a connection there to disconnect that client. API Keys lists manually generated keys; its revoke-all action leaves MCP connections intact. Revocation preserves dashboard and management sessions. `/settings/mcp` provides OAuth configuration for Codex, Claude Code, Cursor, VS Code and other Streamable HTTP clients, using the public API origin's `/mcp` endpoint.

Key administration requires a separate root-verified session. `POST /auth/key-management/session` issues a random `vlm_` token, stored only as a SHA-256 digest, bound to `urn:vitalog:key-management` and the `keys:manage` scope, and valid for 30 minutes. It can list/create/revoke external keys through `/auth/key-management/api-keys`; it cannot access health REST, MCP, readiness, OpenAPI, or the primary `/v1/api-keys` routes. A dashboard `vls_` token can call only `GET /auth/key-management/api-keys`, so browsing keys does not require reauthentication. Creation and revocation still require the root-verified management session. Migration `0010` fixes management-key expiry at 30 minutes and permits the management scope only on its separate resource; OAuth authorization codes remain restricted to health scopes.

The Next.js settings proxy validates the dashboard session for every request and requires the separate management token only for creation and revocation, checks the configured Origin for mutations, and keeps the latter in a host-only HttpOnly SameSite=Lax cookie (`__Host-vitalog-key-management` on HTTPS, `vitalog-key-management` on loopback). Session tokens, root credentials and the environment `AUTH_KEY` never appear in browser JSON or persistent browser storage. Management expiry prompts fresh verification when creating or revoking; browsing remains available. Logout revokes and clears both sessions. No extra UI environment secret is required.

## Verification and local preview

`npm run test:web` runs the production Next.js build against a disposable PostgreSQL database and the real Hono API. Run `npm run build:web` first, and install the browser with `npx playwright install chromium` (CI also installs system dependencies). For an existing local Chromium executable, set `PLAYWRIGHT_CHROMIUM_EXECUTABLE`. The suite checks privilege boundaries, login toasts, cookie privacy, responsive layouts, missing/zero values, logs, weight baseline/progress and revocation. Screenshots and the report are written under the ignored `.test-artifacts/` directory.

`npm run preview:web` starts a disposable synthetic preview and leaves it running until interrupted. Its loopback URLs and random test credentials are saved with owner-only permissions in `.test-artifacts/web/preview.json`. It does not use the repository's `.env` database or personal records. For normal development, use `npm run dev` and `npm run dev:web` with the existing environment configuration.
