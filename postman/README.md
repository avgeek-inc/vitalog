# Postman

Vitalog keeps API documentation in the repository. `collections/Vitalog API` and `environments/Vitalog.environment.yaml` use Postman's Native Git layout, matching Towbar's repository approach. `Vitalog.postman_collection.json` and `Vitalog.postman_environment.json` can also be imported into a regular Postman workspace.

Select the Vitalog environment and set `baseUrl` to the service origin, without `/v1`. Enter `authKey` as a private local secret value. The collection inherits its Bearer authentication from that variable. Never put the key in request bodies, URL parameters, exported environments or shared variable values.

The API keys folder includes generation, listing, individual revocation and revoke-all. Set `rootEmail` and `rootPassword` as private local values only for generation. That request explicitly disables inherited Bearer authentication and sends the root credentials in its JSON body. Set `rootAuthKey` to the environment `AUTH_KEY` for administration; these requests override the collection's ledger Bearer key. Copy a generated key into `authKey` to use it for REST/MCP and set `apiKeyId` from creation or listing before individual revocation. Generated keys cannot perform administration. Complete keys are shown only by generation and expire after 30 days. Do not save response tokens or root passwords in shared/exported environments.

Set `date` to the local calendar date being queried. Set `recordId` from a saved record's `id`. Set a fresh `idempotencyKey` for each intentional mutation and retain it for retries. The API requires that key in `Idempotency-Key` for REST and `idempotency_key` for MCP. A correction or void also needs the record's current `expected_version`; retrieve the record first.

All bodies are synthetic historical examples. Executing a logging, correction or void request changes the configured database. Use a disposable instance for exploration. The collection does not seed a database or run writes merely by being imported.

For MCP, run Initialize, then Initialized notification, then List tools. Tool calls use `POST /mcp`, `Accept: application/json, text/event-stream`, and the negotiated protocol header. Vitalog uses a fresh stateless SDK transport per HTTP request and has no persistent MCP session ID. GET with an SSE Accept header and DELETE follow the selected SDK's stateless behavior; both still require authorization. Missing/unsupported Accept or protocol headers return SDK transport errors.

The collection has 30 REST/technical requests, 30 MCP requests, 4 API-key requests, 8 OAuth requests 3 browser-session requests and 7 key-management requests. The MCP group includes initialization, the initialization notification, tool listing and all 27 tools. The REST group includes every domain route, liveness, readiness and authenticated OpenAPI. Set `goalId` from a saved goal for retrieval or archival. For a new goal use `expected_version: 0`; retrieve the current goal version before editing or reactivating it. See the [goals guide](../docs/goals.md) for comparison and progress semantics.

The OAuth group documents protected-resource and issuer discovery, authorization, browser consent context, approval, client registration and token exchange. Disable inherited Bearer authentication for these requests. Approval sends private `rootEmail` and `rootPassword` variables only in its JSON body; cancel does not need credentials. For a local protocol check, set `PUBLIC_BASE_URL` to the exact loopback origin, choose an opaque `oauthState` and a 43–128 character PKCE `oauthVerifier`, and derive `oauthChallenge` as unpadded base64url SHA-256 of that verifier. Run authorization to establish the flow cookie, read the request's `csrf_token` into the private `oauthCsrf`, and approve. Copy the callback's code into private `oauthCode` and exchange it with the same verifier. Codes last five minutes and can be used once. Exchange creates a scoped 30-day MCP token, which the primary `AUTH_KEY` can manage through the API-key endpoints. Keep credentials, cookies and these variables local; do not export them. MCP clients perform these steps automatically; see [the OAuth guide](../docs/oauth.md). Set `oauthClientId` and `oauthRedirectUri` to your client’s metadata URL and registered callback. For dynamic registration, set `oauthClientName` and `oauthRedirectUri`, run Register OAuth client and use the returned `client_id` for authorization and exchange. The example explicitly requests a public client (`none`). Confidential clients must send their returned secret through their declared Basic or POST authentication method.

The Browser sessions folder creates a read-only 30-day session using root credentials, checks its status and revokes the authenticated session. Copy the returned `session_token` into the private local `browserSessionToken` variable for the latter two requests. These tokens cannot write health data, manage keys or access MCP. The UI normally keeps the token in an HttpOnly cookie rather than exposing it to browser JavaScript. See [the viewing UI guide](../docs/web.md).

Run `npm run docs:generate` to regenerate OpenAPI, schemas, coverage metadata and both Postman formats. `npm run docs:check` fails when a checked-in artifact is stale. The integration suite exercises the same domain schemas through HTTP and the official MCP client; a generated collection alone is not live API test evidence.

The default `baseUrl` is `https://vitalog-api.praveent.com`. `uiUrl` is `https://vitalog.praveent.com` and supplies the Origin header for OAuth approval. For loopback use `http://127.0.0.1:3000` and `http://127.0.0.1:3001`. Authorization first sets the API-host cookie and redirects to the separate UI; do not enable automatic redirect following when inspecting the code flow in Postman.

The Key management folder exchanges root credentials for a separate 30-minute session. Copy its `session_token` into the private local `keyManagementToken` variable, then check or revoke that session and list, create or revoke generated keys and MCP connections. These endpoints exclude browser and management sessions; revoke-all preserves the current browser session. This token cannot access health records, MCP or primary-key administration. The Settings UI keeps it in a separate HttpOnly cookie.

For attachments, calculate the original file's byte length and SHA-256 locally, then set `attachmentByteLength` (a number) and `attachmentSha256`. Run `health_create_attachment_upload` through REST or MCP and set `attachmentId` from the result. Send the file with a separate PUT request to `upload.url`, use the returned Content-Type/Content-Length and select Body → binary in Postman. Disable inherited authentication on that PUT: do not send your Vitalog Bearer key to S3. Run `health_complete_attachment_upload`, then reuse the ready ID in top-level `attachment_ids` on logging/correction requests. Signed URLs are temporary private capabilities and should not be exported or shared. See the [attachment guide](../docs/attachments.md).
